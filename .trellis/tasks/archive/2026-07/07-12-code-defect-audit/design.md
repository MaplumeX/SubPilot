# 缺陷排查设计

## 审查边界

以用户可见的端到端数据流为主线审阅：认证 → API 请求 → 数据持久化 → 订阅生命周期 → 统计/预测/日历 → 提醒与前端呈现。另行检查部署配置和安全边界。

## 证据分级

- **已复现**：静态检查、构建、测试或最小运行验证直接失败。
- **代码可证实**：控制流或数据契约在特定合法输入下必然出错，附精确路径。
- **待验证**：依赖外部服务或运行环境，不能直接确认；不作为已确认缺陷报告。

## 严重性

- P0：越权、数据泄露/损坏、应用不可用。
- P1：核心订阅、金额、续费、提醒或登录流程在常见输入下错误。
- P2：特定边界条件或明显体验问题，有可接受的绕行方式。
- P3：低影响问题；仅在证据充分时报告。

## 约束

不覆盖用户现有未提交改动。验证使用可逆的读取、构建、静态检查和临时数据。

## 修复设计

- 启动配置必须拒绝已知开发默认密钥；Compose 不再提供该密钥的回退值。
- 本地 logo 上传仅允许 PNG/JPEG/GIF；缓存的远程 logo 使用相同白名单，避免将 SVG 作为同源主动内容托管。
- 货币使用与用户基础货币一致的支持货币集合；支付方式更新字段保持非空，非法输入由 Pydantic 返回 422。
- Axios 401 拦截器在仅一次重试内调用 refresh 端点，刷新失败后才清理令牌并跳转；避免刷新请求自身递归。
- 将 toast 发布函数移出组件模块，使 lint 的 Fast Refresh 规则通过。
